## Приоритетные находки

### P1. Подготовка Smudge блокирует обработку первого касания

`SmudgeCanvasView.swift`: `makeUIView` вызывает `snapshotCanvas` непосредственно в `onTouchBegan`, когда renderer.needsSnapshot. Снимок создаётся через SwiftUI ImageRenderer в масштабе экрана. Далее `MetalSmudgeRenderer.updateBaseTexture` выделяет CPU-массив пикселей, рисует CGContext, загружает текстуру; `copyBaseToInteractive` вызывает `waitUntilCompleted` в том же пути. Координатор работает на MainActor.

После окончания relaxation `draw` устанавливает `isBaseInitialized_ = false`. Поэтому это не только первый жест за запуск: новый жест после полного затухания снова требует снимок и ожидание GPU. Смена только названия async-метода проблему не решит: необходимо убрать синхронное ожидание из обработчика ввода и организовать безопасную подготовку/переиспользование ресурсов.

### P1. Ограничение вычислений кисти не убрало полноэкранную стоимость движения

`MetalSmudgeRenderer.applySmudge` перед каждым участком следа копирует целиком две текстуры (изображение и возраст), затем запускает compute внутри границ кисти. Аккумулятор допускает четыре участка на палец за кадр. `applyRelaxDiffuse` затем обрабатывает всю текстуру, после чего идёт полноэкранный display. Smudge работает на 60 FPS; разрешение его текстур определяется снимком в масштабе экрана.

Это подтверждённый источник нагрузки на пропускную способность памяти. Для определения его доли нужен GPU-профиль. Оптимизацию следует сравнивать по кадрам с Legacy: простое уменьшение количества участков уже влияет на форму следа. При накоплении более четырёх участков аккумулятор объединяет соседние отрезки, поэтому при задержках теряет детали траектории. Фильтр SmudgeTouchPathFilter в текущем callback сглаживает данные для gesture/audio, а визуальные `addStrokeSegment` получают исходные previous/current.

### P1. Первый фон намеренно появляется позднее содержимого

`TodayCanvasBackground.swift`: singleton начинает с `image == nil`; готовый растр не сохраняется между запусками. Первый render, как и последующие, ждёт debounce 180 мс. До изображения показывается Night.background; после render изображение подставляется без отдельного перехода готовности. Это дефект добавленного мной общего фона.

На MainActor выполняются чтение/кодирование локального Canvas, подготовка входных данных экспорта и Legacy SwiftUI ImageRenderer. Editorial export тоже создаёт новый DayObjectsRenderer, но фактический executor его async-функции следует проверить в профиле; наличие await само по себе не является измерением блокировки UI.

Дополнительный дефект: nil-результат render записывается в image, а запрос отмечается completed. Это может убрать прежнее изображение и не повторить попытку при следующем идентичном refresh. Нужны сохранение последнего успешного изображения и политика повторной попытки.

### P1. Постеры создают Metal ресурсы на главном потоке; экспорты повторяют setup

`DayObjectsMetalView.Coordinator.init` помечен MainActor и синхронно вызывает DayObjectsRenderer.create. Каждый renderer создаёт command queue, library и шесть pipeline states. `DayObjectsImageRenderer.image` делает то же для каждого экспорта. Driver может кэшировать компиляцию, но общего кэша этих pipeline objects в данном пути нет.

MeSelectedDayPoster материализует DayCanvasArtworkView после подготовки artwork. Постер создаёт собственный рендерер, даже при наличии общего фонового UIImage. Карусель может материализовать соседние страницы; отключение их анимации не отменяет создание renderer и статический кадр. При этом существующее ограничение активной анимации выбранным постером правильное: все постеры непрерывно не анимируются.

### P2. Сохранение Canvas разветвляет работу на несколько экспортов

Gallery.loadCanvas вызывается при onAppear и может вызвать syncCanvasWithModel/saveCanvasLocally. Сохранение уведомляет общий фон; Gallery.publishCanvasPersistence отдельно запускает widget snapshot, remote sync и уведомляет историю. Видимый Canvas, экспорт виджета и экспорт фона не разделяют один готовый результат. Рабочая очередь фонового store объединяет только собственные запросы, а не все эти экспорты.

Нужно объединение по ключу визуального состояния и приоритет видимого первого кадра. Длительность и фактическое число экспортов при одном переключении ещё нужно измерить.

### P2. Повторное открытие Me запускает загрузку сегодняшнего постера

MeSelectedDayPoster использует forceRefresh для сегодня при task и при переходе renderingIsActive false → true. Существующее изображение сохраняется политикой visibleArtwork; чтение coordinator вынесено в detached task. Поэтому сам этот код не доказывает обязательный чёрный экран при возвращении. Но обновление данных может повторно построить сцену и статический/живой кадр.

На корневом TabView стоит общая анимация selection 0,2 с. Вкладки материализуются лениво. Нужна покадровая запись, чтобы отделить переход контейнера от запаздывания содержимого/Metal drawable. При обычной смене вкладки TodayCanvasBackdropStore не очищает image; утверждать обратное было бы ошибкой.

## Порядок исправления и проверки

1. Зафиксировать точную сборку и снять холодный старт, первое и повторное Canvas → Feeds → Me, Smudge после затухания, Smudge со звуком. Отдельно Release на устройстве. Замеры: время до первого содержательного кадра, длительность чёрного промежутка, main-thread hitches, GPU duration; CPU и GPU анализировать отдельно.
2. Убрать пустой первый фон: мгновенный лёгкий fallback из сегодняшней палитры, кэш готового растра с ключом дня/оформления, без debounce для первого показа, сохранение последнего успешного результата. Не показывать вчерашнее искусство под видом сегодняшнего.
3. Разделить общие immutable Metal resources и состояние отдельных сцен. Перенести допустимую подготовку с MainActor, показывать готовый постер до первого живого кадра. Объединить дублирующиеся экспорты.
4. Убрать ImageRenderer и GPU wait из начала касания Smudge, затем оптимизировать копирования и relaxation. Проверять одновременно скорость и визуальное совпадение: водяное ощущение, круги от тапа, кривые, несколько пальцев, восстановление после паузы.
5. После этого проверить переходы TabView; менять навигационный контейнер только если запись подтвердит его вклад. Не скрывать блокировку увеличенной длительностью анимации.

Unit-тесты и скриншоты после ожидания стабильного состояния не ловят эти дефекты. Для приёмки нужны запись переходов и измерение кадров на реальном устройстве. Production-правки, установка и push в этом проходе не выполнялись.
